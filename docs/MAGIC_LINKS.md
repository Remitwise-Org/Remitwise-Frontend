# Magic Links (Nonce-Based Authentication)

Magic links are single-use, time-limited nonce tokens used in RemitWise's
challenge-response authentication flow. A user proves wallet ownership by
signing a nonce with their Stellar private key; the server verifies the
signature and creates an encrypted session cookie.

## Where They Come From

Nonces are generated in `app/api/auth/nonce/route.ts`:

```
const nonce = randomBytes(32).toString('hex');
```

Each nonce is a 32-byte cryptographically random hex string (64 hex chars).
It is stored in an in-memory `Map` keyed by the user's Stellar public address.

## How to Trigger

### Request a nonce

```http
GET /api/auth/nonce?address=GDEMOX7DZZN6Z6B6V6O6W6X6Y6Z6A6B6C6D6E6F6G6H6I6J6K6L6M6N6O
```

Or POST with a JSON body:

```http
POST /api/auth/nonce
Content-Type: application/json

{ "address": "GDEMOX7DZZN6Z6B6V6O6W6X6Y6Z6A6B6C6D6E6F6G6H6I6J6K6L6M6N6O" }
```

**Response (200):**

```json
{
  "nonce": "a1b2c3d4e5f6...",
  "address": "GDEMOX7DZZN6Z6B6V6O6W6X6Y6Z6A6B6C6D6E6F6G6H6I6J6K6L6M6N6O",
  "expiresAt": "2026-07-25T12:05:00.000Z"
}
```

### Authenticate with the signed nonce

The client signs the raw nonce bytes with the Stellar wallet (e.g., Freighter)
and submits the signature:

```http
POST /api/auth/login
Content-Type: application/json

{
  "address": "GDEMOX7DZZN6Z6B6V6O6W6X6Y6Z6A6B6C6D6E6F6G6H6I6J6K6L6M6N6O",
  "message": "a1b2c3d4e5f6...",
  "signature": "MEUCIQD..."
}
```

**Response (200):**

```json
{
  "success": true,
  "address": "GDEMOX7DZZN6Z6B6V6O6W6X6Y6Z6A6B6C6D6E6F6G6H6I6J6K6L6M6N6O",
  "expiresAt": "2026-08-01T12:00:00.000Z"
}
```

A `Set-Cookie` header is returned with the encrypted session.

## TTL

| Token | Default TTL | Configurable | Source |
|---|---|---|---|
| **Nonce** | 5 minutes | No (hard-coded) | `lib/auth-cache.ts:18` |
| **Session cookie** | 7 days | Yes (`SESSION_MAX_AGE`) | `lib/session.ts:48` |

### Post-auth

Once the session cookie is set, the browser sends it automatically on every
request. The server validates the encrypted cookie on each protected route
via `requireAuth()` or `getSession()`.

### Session refresh (optional)

When `SESSION_REFRESH_ENABLED=true`, `getSessionWithRefresh()` extends the
session expiry on each read while preserving the original `createdAt`. When
disabled (default), the session expires at its original deadline regardless
of activity.

### Logout

```http
POST /api/auth/logout
```

Clears the session cookie via `clearSessionCookie()` (sets `Max-Age=0`).

## Known Limitations

### 1. In-memory nonce cache

Nonces are stored in a plain `Map<string, NonceEntry>` in
`lib/auth-cache.ts`. This means:

- **Nonces are lost on server restart** — any in-flight authentication
  attempts fail with "Invalid or expired nonce".
- **Nonces do not scale across multiple instances** — if the app runs
  behind a load balancer without sticky sessions, a nonce generated by
  one instance will not be found by another.

For production deployments with more than one instance, swap the in-memory
store for a shared store (Redis, database).

### 2. Single-use nonces

`getAndClearNonce()` atomically reads and deletes the nonce entry. This
prevents replay attacks — the same signed message cannot be used to
authenticate twice.

### 3. One nonce per address

Calling `GET /api/auth/nonce` for the same address overwrites the
previous nonce. If a user requests a new nonce before completing the
login, the old nonce is invalidated.

### 4. Rate limited

Auth endpoints (`/api/auth/*`) are limited to **10 requests per minute
per IP** in the global middleware (`middleware.ts:268-270`). This applies
to the nonce endpoint too, so aggressive retries will get `429 Too Many
Requests`.

### 5. No persistence

The nonce cache has no backup or persistence layer. A process crash or
deployment roll during an active auth flow invalidates all outstanding
nonces.

### 6. Session cookie constraints

- Requires `SESSION_PASSWORD` (at least 32 characters) in the environment
  — without it the server throws at startup.
- Session is a client-side encrypted cookie, not a server-side session.
  There is no way to revoke individual sessions server-side (no session
  blacklist).
- Cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in production.

## Verification

To test the end-to-end flow manually:

```bash
# 1. Request a nonce
curl -s "http://localhost:3000/api/auth/nonce?address=GDEMOX7DZZN6Z6B6V6O6W6X6Y6Z6A6B6C6D6E6F6G6H6I6J6K6L6M6N6O"

# 2. Sign the nonce with your Stellar wallet and submit
curl -s -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"address":"G...","message":"<nonce>","signature":"<base64>"}' \
  -c cookies.txt

# 3. Access a protected route
curl -s http://localhost:3000/api/user/profile -b cookies.txt

# 4. Logout
curl -s -X POST http://localhost:3000/api/auth/logout -b cookies.txt
```

For automated testing, see [TESTING_AUTH.md](TESTING_AUTH.md) and the
integration tests in `tests/integration/auth.test.cjs`.
